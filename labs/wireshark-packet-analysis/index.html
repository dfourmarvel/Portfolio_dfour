Filtering Network Traffic in Wireshark

Cutting a 200-packet capture down to one conversation — filtering by IP address, MAC address, UDP port, TCP port, and payload text.

WiresharkDisplay filtersICMPDNSTCP

A security analyst investigating traffic to a website has to work out which packets actually matter. The capture file sample.pcap holds traffic from a user connecting to an internet site — 200 packets, unreadable line by line. The task was to filter it down enough to identify the source and destination addresses in the browsing session, examine the protocols carrying the connection, and inspect individual packets to see what the connected systems sent each other.

Task 1 — Explore data with Wireshark

Each packet is a row with seven columns: index number, timestamp, source and destination IP, protocol, total length, and Wireshark's interpretation of the payload. Colouring rules classify traffic at a glance — light blue for DNS, green for a mixture of TCP and HTTP. Scrolling to the first packet whose Info column starts with Echo (ping) request gives the first answer: the protocol is ICMP.

Task 2 — Apply a basic filter and inspect a packet

Filtering on a single address returns packets where it appears as either source or destination.

display filter
ip.addr == 142.250.1.139

The list drops from 200 packets to 16 — 8.0% of the capture — and only two colours remain: light pink for ICMP and light green for TCP, of which HTTP is a subset.

Opening the first TCP packet splits it into one subtree per layer. Frame gives the overall packet length and arrival time. Ethernet II gives the source and destination MAC addresses and the protocol carried inside. Internet Protocol Version 4 gives the IP addresses — matching the summary row — and the internal protocol. Transmission Control Protocol gives the ports, sequence numbers and flags. The destination port is 80.

Task 3 — Use filters to select packets

Three narrower filters separate traffic by origin, by destination, and by physical interface.

display filter
ip.src  == 142.250.1.139
ip.dst  == 142.250.1.139
eth.addr == 42:01:ac:15:e0:02

The source filter returned 7 packets (3.5%), the destination filter 9 (4.5%). The MAC filter is different in kind — it selects traffic to or from one Ethernet address regardless of the other protocols involved. Opening its first packet and expanding the IPv4 subtree to the Time to Live and Protocol fields shows the internal protocol is TCP.

Task 4 — Explore DNS packets

DNS runs over UDP port 53, so this returns queries and responses only — 22 packets, 11.0% of the capture.

display filter
udp.port == 53

Expanding Queries on the first packet shows the name being looked up: opensource.google.com. Expanding Answers on the fourth shows that name alongside the addresses returned for it, including 142.250.1.139 — the address the browsing session went on to use.

Task 5 — Explore TCP packets

Port 80 is the default for web traffic, so this selects the packets created when the user loaded http://opensource.google.com — 26 packets, 13.0%.

display filter
tcp.port == 80

The first packet in that list has a destination of 169.254.169.254, a Time to Live of 64, a frame length of 54 bytes, and an IPv4 header length of 20 bytes.

The last filter searches payload text rather than headers, matching packets that carry a specific string — here, the web requests issued with curl.

display filter
tcp contains "curl"

key takeaway

Practical experience opening saved capture files, reading high-level packet data, and using filters to inspect it in detail. Each filter answers a different question — an IP filter follows a conversation, a MAC filter follows an interface, a port filter follows a service, and a content filter follows a string in the payload.
