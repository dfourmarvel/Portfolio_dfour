Applying Filters to SQL Queries

Isolating suspicious activity with AND, OR, NOT, and LIKE across login and employee tables.

MariaDBAND / OR / NOTLIKEWildcards

After-hours failed logins (AND)

Two conditions joined with AND — both must be true — isolated failed login attempts after 18:00. The query returned 19 rows.

sql
SELECT *
FROM log_in_attempts
WHERE login_time > '18:00' AND success = 0;

Logins outside Mexico (NOT + LIKE)

The country column stored Mexico as both MEX and MEXICO, so a simple equality check would miss a variant. LIKE 'MEX%' matches any string starting with "MEX"; wrapping it in NOT returns every other country — a robust way to handle inconsistent data.

sql
SELECT *
FROM log_in_attempts
WHERE NOT country LIKE 'MEX%';

Targeted patching (AND + LIKE, OR, NOT)

  • Marketing staff in the East building: department = 'Marketing' AND office LIKE 'East%' — 7 employees.
  • Finance or Sales (an employee is in one department, so OR, not AND): department = 'Finance' OR department = 'Sales'.
  • Everyone except already-patched IT: NOT department = 'Information Technology' — concise and future-proof.

key takeaway

Clean queries save investigations. LIKE with wildcards proved essential for messy real-world data ("MEX" vs "MEXICO", variable room numbers), and knowing when to reach for AND vs OR vs NOT is the difference between finding an active threat and getting lost in the noise.
