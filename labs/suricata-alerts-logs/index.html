Suricata Alerts and Logs

One Suricata rule, a 200-packet capture, and the same two alerts read twice: as one-line entries in fast.log and as full records in eve.json.

SuricataIDS rulesjqJSON logspcap

Suricata is an open-source intrusion detection and prevention system: it applies rules to network traffic and decides, packet by packet, whether to alert, drop, reject or let it pass. This lab ran one custom rule against a recorded capture, sample.pcap, then read the alerts it produced in Suricata's two log formats.

Task 1: Read the rule

The supplied custom.rules file held a single signature.

bash
$ cat custom.rules
# alert http $HOME_NET any -> $EXTERNAL_NET any (msg:"GET on wire"; flow:established,to_server; content:"GET"; http_method; sid:12345; rev:3;)

It reads in three parts. The action, alert, logs a match and lets the traffic continue. The header, http $HOME_NET any -> $EXTERNAL_NET any, limits it to HTTP leaving the home network (172.21.224.0/20 in this lab) for anywhere outside. The options narrow it further: flow:established,to_server matches only client-to-server packets on an open connection, and content:"GET"; http_method looks for GET in the HTTP method field, not anywhere in the packet. sid is the rule's ID and rev its revision.

Task 2: Trigger it and read fast.log

The log directory was empty before the run. Suricata then replayed the capture through the rule, with -k none switching off checksum checks that recorded traffic doesn't need.

bash
$ ls -l /var/log/suricata
# total 0
$ sudo suricata -r sample.pcap -S custom.rules -k none
# i: pcap: read 1 file, 200 packets, 54238 bytes
bash
$ cat /var/log/suricata/fast.log

Two alerts out of 200 packets. Each fast.log line carries the time, [1:12345:3] (generator, signature ID, revision), the message, a priority, and source and destination. The classification is (null) because the rule never set one. The lab brief's sample output shows 142.250.1.139 twice; this run's second alert went to 142.250.1.102.

Task 3: The same alerts in eve.json

eve.json is Suricata's main log, one JSON object per event. It held the same two alerts, each with far more attached.

bash
$ cat /var/log/suricata/eve.json
$ jq . /var/log/suricata/eve.json | less
Fieldfast.logeve.json
Addresses and portsyesyes
Alert actionnoallowed
Severityas priority 33

jq can also cut the file down to chosen fields, or to every event from one connection. Each flow gets its own flow_id and every event in it shares that ID, which is how related events are pulled together. No screenshot of these two outputs was kept; the flow IDs above come from the raw records in Figure 4.

bash
$ jq -c "[.timestamp,.flow_id,.alert.signature,.proto,.dest_ip]" /var/log/suricata/eve.json
$ jq "select(.flow_id==X)" /var/log/suricata/eve.json

key lesson

fast.log answers whether a rule fired and against which addresses, which is enough to count alerts while testing a rule. Everything needed to judge an alert sits only in eve.json: the request behind it, the server's reply, the flow_id that ties it to its connection, and the fact that Suricata marked both alerts allowed because it was running as a detector, not a blocker.
