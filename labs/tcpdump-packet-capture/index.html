Capturing HTTP Traffic with tcpdump

Four tcpdump commands, the name resolution it performs by default, and the point where a plain HTTP request becomes readable bytes.

tcpdumpifconfigcurlHTTPpcap

This lab worked through the core tcpdump workflow used to capture and inspect live network traffic on a Linux machine: identifying which network interfaces are available to capture on, inspecting live traffic on the chosen interface, capturing a filtered sample of that traffic to a file, and then reading the saved file back in two different output formats to interpret exactly what was captured.

Task 1 — Identify network interfaces

sudo ifconfig listed the interfaces on the machine. eth0 was identifiable as the Ethernet interface by its "eth" prefix, showing IP address 172.18.0.2 and MAC address 02:42:ac:12:00:02.

bash
$ sudo ifconfig

sudo tcpdump -D then listed every interface tcpdump itself could capture on: eth0, the pseudo-interface any (captures on all interfaces at once), lo (loopback), and several interfaces with no active traffic (bluetooth-monitor, nflog, nfqueue, dbus-system, dbus-session). Between the two commands, eth0 was confirmed as the interface to use for the rest of the exercise.

bash
$ sudo tcpdump -D

Task 2 — Inspect network traffic on an interface

sudo tcpdump -i eth0 -v -c5 captured five packets from eth0, with -v adding detail to each packet's IP and TCP header fields (TTL, ID, flags, checksum, sequence and acknowledgment numbers, window size) and -c5 stopping the capture after five packets. The point of this task was to observe tcpdump's default behaviour: by default, tcpdump resolves IP addresses and ports to hostnames rather than displaying them numerically. That resolution is visible directly in the capture — the lab VM's own hostname and its terminal backend's hostname appear in place of raw IP addresses, on port 5000, and a DNS PTR lookup addressed to metadata.google.internal shows up among the five packets. This is exactly the default behaviour that -nn is used to switch off in Tasks 3 and 4. The resolved backend hostname was nginx-us-central1-b.c.qwiklabs-terminal-vms-prod-00.internal.

bash
$ sudo tcpdump -i eth0 -v -c5

Task 3 — Capture network traffic to a file

sudo tcpdump -i eth0 -nn -c9 port 80 -w capture.pcap & started a background capture on eth0, filtered to port 80 (HTTP) traffic, limited to nine packets, and written to capture.pcap rather than printed to the terminal. The -nn flag disabled IP address and port name resolution — a security best practice, since lookup data may not be reliable and performing lookups can alert anyone monitoring the network that an investigation is under way.

bash
$ sudo tcpdump -i eth0 -nn -c9 port 80 -w capture.pcap &

With the capture running, curl opensource.google.com generated the HTTP traffic to capture: curl's own output showed the site responding with a 301 Moved redirect to https://opensource.google/.

bash
$ curl opensource.google.com

The background job then reported "[1]+ Done" once its nine-packet limit was reached, and ls -l capture.pcap confirmed the file existed on disk (1401 bytes).

bash
$ ls -l capture.pcap
# -rw-r--r-- 1 tcpdump tcpdump 1401 Aug 14 22:40 capture.pcap

Task 4 — Filter the captured packet data

Two commands read the same capture.pcap file back in different formats. sudo tcpdump -nn -r capture.pcap -v reproduced the verbose per-packet detail from Task 2, this time reading from the saved file rather than from live traffic, again with -nn disabling name resolution for the same investigative reasons as Task 3. The read-back showed the TCP three-way handshake between 172.18.0.2 and 173.194.206.101 on port 80 (SYN, SYN-ACK, ACK), each packet's TTL and checksum-verification status, and, further into the exchange, the full HTTP response: HTTP/1.1 301 Moved Permanently, a Location header pointing to https://opensource.google/, and further headers including Content-Type, Cache-Control, Server, and X-XSS-Protection.

bash
$ sudo tcpdump -nn -r capture.pcap -v

Then sudo tcpdump -nn -r capture.pcap -X read the same file a second time, printing each packet's raw bytes in hexadecimal alongside their ASCII equivalent. This is the format analysts use to look for patterns or anomalies during malware or forensic analysis. In this capture, the ASCII column of the fourth packet showed the HTTP GET request in full, human-readable text: "GET / HTTP/1.1", "Host: opensource.google.com", "User-Agent: curl/7.74.0", and "Accept: */*" — the same request that the -v output in the previous command had already interpreted and labelled, now visible as the literal bytes it was built from.

bash
$ sudo tcpdump -nn -r capture.pcap -X

key takeaway

Reading the same file with -v and then with -X made the distinction between those two formats concrete: -v labels and interprets the header fields for you, while -X shows the underlying bytes those labels were built from — and in this capture, because the traffic was plain HTTP rather than HTTPS, those underlying bytes included a fully readable GET request.
