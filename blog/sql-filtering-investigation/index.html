Investigating a breach with raw SQL

Jun 1, 2026 sql google cybersecurity certificate lab

Completed a SQL filtering lab as part of my Google Cybersecurity Certificate — and it's one of the more practical exercises I've done so far.

The scenario: a potential breach at a fictional organization. My job? Investigate it using only raw SQL queries—no dashboards, no shortcuts.

Here's the breakdown of the investigation:

Isolating Threat Windows: Filtered the log_in_attempts table to catch after-hours failed login attempts after 18:00, extracting 19 critical rows.

Timeline Mapping: Pulled all login records spanning two specific suspicious dates using OR logic.

Geofencing Traffic: Excluded logins originating from Mexico using NOT + LIKE to account for real-world data inconsistency where the country was recorded as both 'MEX' and 'MEXICO'.

Targeted Patching: Pivoted to the employees table to identify 7 specific Marketing machines located in the East building using wildcards ('East%').

Access Segregation: Isolated Finance and Sales staff for critical system updates, and excluded IT personnel who had already been patched using the NOT operator.

The biggest takeaway? Clean queries save investigations. Knowing exactly how to handle conditional operators and wildcards is the difference between finding an active threat and getting lost in the noise.
