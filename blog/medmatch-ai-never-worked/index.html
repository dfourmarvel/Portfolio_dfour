The AI feature that had never worked

Sep 09, 2026 web project from linkedin

The AI feature on my app had never worked. Not once, for anyone, in the four months since it shipped.

MedMatch Ghana gives medical students a specialty-fit assessment, and part of the results page was meant to be an AI-written explanation of why your top three matches came out the way they did. I was reading the route handler for an unrelated reason when I noticed it was validating a request shape (a user id, an answers array, a list of top specialties) that the results page had stopped sending long ago. The page posts the full assessment result object. The route rejected it. Every live request returned a 400.

Nobody saw an error, because the client caught the failure and showed a friendly fallback message instead. It looked intentional. It looked like a product decision. Every person who ever finished the assessment got the fallback, and nobody reported anything, because there was nothing visibly broken to report.

Three days later I found the same shape of bug somewhere else. A scheduled job kept my free-tier Supabase project awake by calling a results endpoint with a zeroed UUID and treating the 404 as proof of life. That function returns not-found when the row is missing, when the database client fails to initialise, and when the query itself errors. All three come back as 404. The check reported green with the database completely unreachable, which is the one condition it existed to detect. I replaced it with an endpoint that runs a real head query and answers 200 or 503, then confirmed it returns 503 against placeholder credentials, exactly the case the old one called healthy.

Both are the same mistake. I built systems that degrade gracefully, and they degraded so gracefully that nothing ever told me they were degrading.

The clinical version is familiar. A patient in compensated shock has a normal blood pressure. The number is real, it is reassuring, and it is the last thing you should trust, because the body is holding that reading up at a cost the monitor cannot show you. Normal vitals are not a well patient, and a passing health check is not a working system.

The limitation worth stating: I found both of these by reading my own code, not from monitoring, which is itself the finding. That project has no error tracking and no alert on 4xx rates. With either one, the first bug surfaces in a day instead of four months.

If you run something small in production, I would like to know what your cheapest signal is that a fallback path has quietly become the only path.
